# テスト要求仕様（TRS）

## 目的

テスト設計の前に、対象がどう動くべきかを確定し、確認に使う因子と水準まで決めておく。何を確認するかを先に固定することで、テストケースの切り分けが書き手の勘に依存しなくなる。

この文書は Yoriwake に TRS を適用する方法と、このリポジトリでの具体的な内容を示す。実装方式や内部設計は扱わない。

## TRS の考え方

TRS は2つの層でできている。仕様レイヤーで「あるべき振る舞い」を確定し、テスト設計レイヤーで「それをどう検証するか」を定義する。読む順番も書く順番も、仕様レイヤーからテスト設計レイヤーへの一方向にする。

仕様レイヤーは、ユースケースとその振る舞い、受け入れ基準（AC）で構成する。振る舞いは正常・準正常・例外の3つに分ける。正常はそのまま成功する。準正常はハンドリング済みのエラーが起きるが再操作で完了できる。例外はユースケースが中断し完了できない。該当が無ければ「なし」と明示する。何も書かないのか、検討して無かったのかを区別するためである。

テスト設計レイヤーは、因子と水準を持つ。AC には `<...>` の可変部だけを書き、どの値でテストするかは因子表が単一情報源として持つ。同じ値を AC 側とテスト側に二重に書かない。

期待値の根拠は仕様書とデザインに限る。実装は「その状態を作れるか」を確かめるためだけに見る。仕様書とデザインのどちらにも書かれていなければ、UNSPECIFIED として扱い、未定義のまま実装で埋めない。埋めると未決事項が消えるためである。

## このリポジトリでの対応

- 仕様レイヤーは `requirements-analysis.md` を母体にする。REQ をユーザー要求、SPEC を外部から観測できる振る舞い、BDD を受け入れ基準とする。Yoriwake では BDD の ID を AC の ID として使う。
- 振る舞いの分類は `requirements-analysis.md` の BDD 表に持つ。
- 不変条件は `domain.md` の `INV-TM-xxx` とし、ADR 0046 の方式でテストと突き合わせる。
- API の在庫は domain-blueprint がコードから生成する `graph.auto.json` と `domain-model.json` を正本とする。OpenAPI は持たない。
- 受け入れ基準とテストの対応は、別ファイルの対応表ではなく、テスト名に含めた ID と機械検証で保つ。対応表はそれ自体が古くなるため、ADR 0046 と同じく採用しない。

## 因子表

テスト設計で値を変える可変データを因子と呼ぶ。因子の値の集合を水準と呼ぶ。AC の `<...>` はこの因子と1対1で対応する。

| 因子 | 水準 |
| --- | --- |
| F-01 認証状態 | 認証済み / 未認証 |
| F-02 対象エンティティ | task / idea / image |
| F-03 status | do / done / skip |
| F-04 area | 1 / 2 / 3 / 4 |
| F-05 working | true / false |
| F-06 title 長 | 空 / 1 / 256 / 257 |
| F-07 description | 空 / 16,384 / 16,385 / URL を含む |
| F-08 version | 最新 / 古い（競合） |
| F-09 order | 有効 / 競合 / 範囲外 |
| F-10 bulk 対象 | 全成功 / 一部競合 |
| F-11 status filter | 指定なし / is:do / is:done / is:skip / 不正 |
| F-12 label filter | なし / label:working / working only |
| F-13 page | 範囲内 / 0 / 負 / 非数値 / 超過 / 25 境界 |
| F-14 画面 | matrix / list / detail / new / preview |
| F-15 pinned | true / false |
| F-16 操作 | 作成 / 更新 / 削除 / 並べ替え / pin |

水準を増やすと組み合わせが急に増える。入力系の因子を全組み合わせで試さず、境界と代表値を選ぶ。この選定は因子表の水準欄に残し、なぜその値なのかを後から辿れるようにする。

## 導入手順

Phase 0 で因子とロールを確定する。上の因子表を出発点にする。

Phase 1 で `requirements-analysis.md` を TRS の形式へ寄せる。SPEC をユースケース、BDD を AC とみなし、BDD 表に振る舞いの分類を加える。

Phase 2 で因子水準表を仕様文書に置く。値の正本を1箇所に集める。

Phase 3 で AC の ID とテストの対応を機械検証する。テスト名に ID を含め、定義側と参照側の dangling、orphan、missing を検出する。検証は `scripts/ci/` のチェッカーで行う。

Phase 4 で `bdd-test-mapping.md` を廃止し、対応の維持を CI ゲートに移す。

## アンチパターン

実装を読んで期待値を決めると、テストは「コードがコード通りに動く」ことの確認になり、仕様と実装のズレを見つけられなくなる。

受け入れ基準とテストの対応を別ファイルの表で持つと、表だけが古くなる。ID と機械検証で持つ。

生成物を手で編集すると、次の生成で上書きされる。正本は入力側に置く。

入力系の因子を全組み合わせで試すと、テスト数が爆発して保守できなくなる。境界と代表値を選ぶ。

## チェックリスト

- 各 AC に振る舞いの分類があり、該当が無い分類は「なし」と書いてある。
- AC の可変部が因子表の因子と対応している。
- 期待値の根拠が仕様書かデザインにあり、実装を根拠にしていない。
- 未定義の事項が未決事項に残っている。
- AC の ID がテスト名に含まれ、機械検証が通る。
