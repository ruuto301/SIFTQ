# ADR 0073: 本番の認証付きスモークを署名済みセッションで自動実行する

## 決定

- 本番の認証付きスモークは、セッション署名鍵から生成した署名済みセッションで認証して実行する。
- アプリには専用の認証経路を追加しない。別の署名鍵を受理する方式や、トークンでセッションを発行するルートは設けない。
- スモークはデプロイが成功した後に自動で実行する。
- 検証で作成したデータには識別可能な印を付け、実施後に削除する。削除に失敗した場合は失敗として扱う。
- 対象は本番環境のみとし、専用の staging 環境は設けない。
- 振る舞いの検証は継続して CI の E2E が担い、本番はデプロイと環境結合の確認に限定する。

### 決定の理由

- セッションはステートレスな署名付き Cookie であり、署名鍵から生成したセッションは本番ログインと等価である。認証を迂回せずに自動化できる。
- アプリに専用経路を足すより、本番の認証面を増やさずに済む。
- デプロイ後に自動実行することで、順序の取り違えによる旧版の検証を防ぐ。
- 作成データの削除を失敗条件にすることで、本番データの残留を防ぐ。

## 不採用

- 別の署名鍵を受理する方式、またはトークンでセッションを発行するルートを追加する
  - 本番の認証面を増やし、管理対象の秘密が増えるため。
- 実 GitHub OAuth を自動化する
  - 二要素認証や CAPTCHA で脆く、資格情報の管理負荷が高いため。
- 専用の staging 環境を新設する
  - 本番のデプロイ結合の確認という目的に対し、基盤のコストが上回るため。
- 本番での認証付き検証を行わない
  - デプロイや環境結合の不備を利用者より先に検出できず、初回アクセスで初めて気づくことになるため。

## 補足情報

### 背景

- 本番の認証付き確認は担当者依存で、手順が固定されていなかった。
- デプロイと環境結合（バインディング、秘密、リモート DB）の不備は開発環境では検出できない。

### 制約事項

- セッション署名鍵は環境変数で供給し、ログや平文ファイルに残さない。
- 署名鍵のローテーションは既存の利用者セッションを無効化する。
- スモークは本番データを作成・削除するため、単一の直列実行に限定する。
- 本番のログイン allowlist や OAuth 設定の正しさは、実 OAuth を通さないため本スモークでは検証しない。

### 限界と再検討条件

- 限界: 実 GitHub OAuth と実利用者の UI 操作は自動検証しない。
- 再検討条件: 利用者ごとの認証や複数利用者対応を始める時、またはデプロイ物に対する認証付き UI 検証を staging で行う必要が出た時。
